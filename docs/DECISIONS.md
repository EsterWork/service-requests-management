# החלטות טכנולוגיות

לכל החלטה: מה נבחר, אילו חלופות נשקלו, למה, ומה המחיר. בסוף המסמך: מגבלות ידועות ושיפורים אפשריים.

---

## 1. בסיס נתונים: SQL Server

| חלופה | יתרונות | חסרונות למערכת הזו |
|---|---|---|
| **SQL Server (נבחר)** | `rowversion` מובנה ל-Optimistic Concurrency; טרנזקציות על כמה טבלאות; `GROUP BY` ואינדקסים מורכבים; תמיכה מלאה ב-EF Core | דורש התקנה של SQL Server |
| MongoDB | גמישות בסכמה; קל לשכפל ולפזר | הנתונים טבלאיים עם מבנה קבוע, כך שהגמישות לא נדרשת. Optimistic Concurrency צריך לממש ידנית (שדה גרסה ותנאי בכל עדכון). עדכון הפנייה ורשומת ה-Audit יחד דורש טרנזקציה על שני מסמכים או הטמעת ההיסטוריה בתוך הפנייה |
| PostgreSQL | דומה ל-SQL Server ביכולות, קוד פתוח | אין `rowversion` מובנה (משתמשים ב-`xmin` או בשדה גרסה). SQL Server כבר היה מותקן בסביבת הפיתוח |

**למה:** הדרישות המרכזיות (סינון ומיון משולבים, Aggregations, עדכון עם Audit באותה טרנזקציה, Concurrency) הן בדיוק מה שבסיס נתונים רלציוני עושה היטב.

## 2. Concurrency: Optimistic עם `rowversion`

| חלופה | למה לא |
|---|---|
| **`rowversion` של SQL Server (נבחר)** | |
| שדה `Version int` שמעדכנים בקוד | עובד, אבל הקוד אחראי להעלות את הגרסה בכל עדכון, ומספיק מקום אחד ששוכח כדי ליצור Lost Update. `rowversion` מתעדכן על ידי ה-DB בכל שינוי של השורה, גם בשינוי שלא עבר דרך הקוד |
| `UpdatedAt` כגרסה | שני עדכונים באותו טיק של השעון יקבלו אותו ערך; תלוי בשעון של השרת |
| Pessimistic Locking (נעילת השורה בזמן העריכה) | המשתמש עלול להשאיר דיאלוג פתוח ולנעול פנייה לזמן לא מוגבל. נעילות לאורך זמן לא מתאימות ל-HTTP ללא מצב |
| הגנה ב-UI בלבד | לא מונעת עדכונים מתחרים מלקוחות אחרים או מבקשות ישירות ל-API |

**איך:** הלקוח שולח את ה-`rowVersion` שקיבל. EF מוסיף `WHERE RowVersion = @original` ל-UPDATE, ועדכון שמשנה 0 שורות מחזיר 409. לפני כן יש בדיקה מוקדמת, שמחזירה 409 בלי לנסות לכתוב, ושבזכותה לא בודקים מעבר סטטוס מול מצב שהלקוח לא ראה. העדכון ורשומת ה-Audit נשמרים באותו `SaveChanges`.

## 3. Bulk: Partial Success, ו-200 גם כשחלק נכשל

| חלופה | יתרונות | חסרונות |
|---|---|---|
| **Partial Success (נבחר)** | התנגשות בפנייה אחת לא חוסמת את האחרות; הלקוח יודע בדיוק מה הצליח ויכול לנסות שוב רק את מה שנכשל | הלקוח צריך לעבור על התוצאות |
| All-or-Nothing | פשוט להבנה: הכול או כלום | בעבודה של כמה משתמשים, ככל שיש יותר פריטים, הסיכוי שאחד מהם השתנה גדל, ואז כל הבקשה נכשלת ויש לנסות הכול מחדש |

**קוד תשובה:** 200, כי הבקשה עצמה תקינה ועובדה במלואה, והתוצאה לכל פריט היא התוכן של התשובה. קוד 4xx היה רומז שלא קרה כלום, בזמן שחלק מהפניות כן עודכנו. `207 Multi-Status` שייך ל-WebDAV ולא מקובל ב-REST API רגיל. 400 מוחזר רק כשהבקשה עצמה לא תקינה (יותר מ-100 פריטים, מזהה כפול וכו').

**מימוש:** טעינה של כל הפניות בשאילתה אחת, ו-`SaveChanges` נפרד לכל פריט, כלומר טרנזקציה לכל פריט. עם `SaveChanges` אחד לכל הפריטים, התנגשות בפריט אחד הייתה מבטלת את כל הטרנזקציה. המחיר: עד 100 פקודות כתיבה נפרדות במקום אחת, וזה זניח בהיקף של 100 פריטים.

## 4. חיפוש טקסט: prefix עם אינדקס, ו-`OPTION (RECOMPILE)`

| חלופה | למה לא |
|---|---|
| **`LIKE 'term%'` (prefix) עם אינדקס על Title ועל OrganizationName (נבחר)** | |
| `LIKE '%term%'` (contains) | לא יכול להשתמש באינדקס; כל חיפוש סורק את כל הטבלה |
| Full-Text Index (`CONTAINS`) | מוצא מילים גם באמצע הטקסט. אבל: דורש SQL ידני ב-Migration; האינדקס מתעדכן באופן אסינכרוני, ולכן בדיקה שמכניסה נתונים ומחפשת מיד עלולה להיכשל לסירוגין; ה-Docker image הרשמי של SQL Server לא כולל Full-Text, וגם LocalDB לא |

**המחיר:** מילה מאמצע הכותרת לא נמצאת (חיפוש "תלוש" לא מוצא "תיקון תלוש שכר"). זה מתועד ונבדק בבדיקת Integration.

**`OPTION (RECOMPILE)`:** במדידות התגלה ש-SQL Server שומר את תוכנית הביצוע של הערך הראשון. תוכנית שמתאימה לחיפוש נפוץ סרקה את כל הטבלה בחיפוש נדיר (306,954 קריאות דפים, 360ms). עם `RECOMPILE`: 10 קריאות ו-4ms, במחיר של כ-3ms קומפילציה לשאילתה. הוא מוחל **רק** על שאילתות החיפוש, דרך `TagWith` ו-`DbCommandInterceptor`. חלופה שנדחתה: `OPTIMIZE FOR UNKNOWN`, תוכנית ממוצעת אחת שלא מתאימה לשני הקצוות. הפירוט ב-[PERFORMANCE.md](PERFORMANCE.md).

**סינון לפי ארגון ומטפל:** גם הוא prefix, ולא התאמה מדויקת. עם התאמה מדויקת, משתמש שמקליד "גליל" לא היה מקבל כלום עד שיקליד את השם המלא. ה-prefix משתמש באותו אינדקס.

## 5. Cache: רק ה-Summary, ב-`IMemoryCache`

| שאלה | החלטה | נימוק |
|---|---|---|
| מה לשמור | רק את ה-Summary | הוא סורק את כל הטבלה בכל קריאה (אינדקס לא עוזר לספירה של הכול), זהה לכל המשתמשים, ומספרים מסכמים בני כמה שניות מקובלים. הרשימה **לא** נשמרת: היא תלויה בפרמטרים של כל משתמש, וחייבת `rowVersion` עדכני |
| איפה | `IMemoryCache` | מופע שרת אחד; אין צורך בתשתית נוספת |
| תפוגה | Absolute, 60 שניות | חוסם את הזמן המקסימלי של נתון ישן, גם במקרה של מירוץ |
| Invalidation | מחיקת המפתח אחרי כל עדכון מוצלח (בודד או Bulk) | המספרים נכונים מיד אחרי עדכון |
| מיקום בקוד | `RequestSummaryService` בשכבת Application | `IMemoryCache` הוא כבר abstraction. המפתח, התפוגה וה-Invalidation נמצאים במחלקה אחת, ומעבר ל-`IDistributedCache` ישנה רק אותה |

**כמה מופעי שרת:** `IDistributedCache` עם Redis (Cache משותף), או Cache מקומי עם Redis Pub/Sub, שבו המופע שעדכן מודיע לאחרים למחוק. הפירוט ב-[README](../README.md#cache-ו-invalidation).

## 6. ארכיטקטורה: ארבעה פרויקטים, בלי שכבות מיותרות

| חלופה | למה לא |
|---|---|
| **Api / Application / Domain / Infrastructure (נבחר)** | |
| פרויקט אחד | Controllers, לוגיקה וגישה ל-DB מעורבבים; קשה לבדוק את הכללים בנפרד |
| MediatR / CQRS | Handler לכל פעולה ושכבת הפניה נוספת, בשביל חמש פעולות. לא פותר כאן בעיה |
| Repository גנרי מעל EF | `DbSet` כבר הוא Repository ו-`DbContext` כבר הוא Unit of Work. Repository גנרי היה מסתיר את `IQueryable`, ואיתו את היכולת לסנן ולמיין ב-DB |

**איך השכבות מתחברות:** Application מגדיר `IApplicationDbContext` (שני `DbSet` ו-`SaveChangesAsync`), ו-Infrastructure מממש אותו. ה-Services כותבים LINQ ישירות, וה-Domain לא תלוי באף שכבה. כללי המעבר נמצאים ב-Domain ([StatusTransitionValidator.cs](../backend/src/ServiceRequests.Domain/StatusTransitionValidator.cs)), במקום אחד.

**תוצאות במקום Exceptions:** שירות העדכון מחזיר תוצאה (`Succeeded / NotFound / InvalidTransition / Conflict`), וה-Controller מתרגם אותה ל-HTTP. כך מצבים צפויים לא עוברים דרך Exceptions, ואותה תוצאה משמשת גם את ה-Bulk, לכל פריט.

## 9. בלי docker-compose

לא נכתב `docker-compose.yml`. בסביבת הפיתוח אין Docker, וקובץ שלא הורץ עלול לא לעבוד אצל הבודק. במקומו, ה-[README](../README.md#הרצה-צעד-אחר-צעד) כולל הוראות הרצה מפורטות, שנבדקו מ-clone נקי של הריפו: Seed, API, Frontend ובדיקות.

## מגבלות ידועות

1. **חיפוש prefix בלבד:** מילה מאמצע הכותרת או שם הארגון לא נמצאת.
2. **ה-Seed לא יוצר היסטוריה:** פניות במצב `Completed` מה-Seed מופיעות עם היסטוריה ריקה. רק שינויים שנעשו דרך ה-API נרשמים ב-Audit.
3. **Cache מקומי:** ב-`IMemoryCache` כל מופע שרת מחזיק Cache משלו. בנוסף, יש חלון מירוץ קטן שבו Summary ישן עלול להישמר אחרי Invalidation, עד 60 שניות לכל היותר.
4. **אין הזדהות:** `changedBy` הוא טקסט חופשי שהמשתמש מקליד (ונשמר בדפדפן לפעם הבאה). במערכת אמיתית הוא יילקח מהמשתמש המחובר.
5. **דפדוף עמוק:** `OFFSET` עובר על כל השורות שלפני העמוד. העמוד האחרון (5,000) לוקח כ-200ms, מול 0ms לעמוד הראשון.
6. **Logging בביטול בקשה:** כשהלקוח מבטל בקשה באמצע שאילתה, ה-Middleware של .NET 8 רושם שורת `fail` אחת, כי SqlClient מדווח על הביטול כ-`SqlException`. אי אפשר לכבות את זה ב-.NET 8.

## שיפורים אפשריים

1. **אינדקס מורכב `(Status, Priority, CreatedAt)`:** נמדד: COUNT עם שני המסננים ירד מ-350 קריאות ל-21. כדאי אם זה שילוב נפוץ.
2. **Keyset Pagination:** נמדד: העמוד האחרון ירד מ-3,398 קריאות ו-224ms ל-66 קריאות ו-0ms. המחיר: אין קפיצה לעמוד N.
3. **Full-Text Index:** חיפוש מילים בכל מקום בטקסט.
4. **Redis:** Cache משותף לכמה מופעי שרת.
5. **הזדהות:** `changedBy` מהמשתמש המחובר, והרשאות לעדכון.
6. **שמירת מצב הסינון והדפדוף ב-URL:** כדי שרענון הדף או שליחת קישור ישמרו את התצוגה.
